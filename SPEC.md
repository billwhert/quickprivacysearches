# Privacy Law Reference Tool: Project Spec

## 1. Purpose

A free, public, searchable reference site for privacy law. It takes official privacy laws, regulations, and guidance, breaks them into small structured pieces, and lets anyone search them and get:

1. The exact source text
2. A citation with a link to the official source
3. Guided research paths that gather the relevant provisions for common real-world questions (for example, "California business privacy notice" or "cookies and tracking")

The site does not use an AI text-generation model. Everything shown is real source text, or a short plain-English summary written and reviewed by me and labeled as a summary. Nothing is generated at the moment a visitor searches.

It runs entirely in the visitor's browser and is hosted as a static site on GitHub Pages at no cost.

## 2. Users

- Primary: me, as a research aid for privacy roles.
- Public: privacy professionals, students, job seekers, and small business owners who open a shared link (for example, on LinkedIn). No login, no account.

## 3. Goals and non-goals

**Goals**
- Fast, precise lookup by section number ("GDPR Article 30") and by concept ("when is a DPIA required").
- Guided research paths that turn a real-world question into a checklist of provisions with exact quotes and citations.
- Every result traceable to an official source, version, and retrieval date.
- Side-by-side comparison of the same topic across laws.
- Permanent shareable links to any provision or guided topic.
- Zero hosting cost and no server to maintain.
- Easy to add new documents later without rewriting code.

**Non-goals**
- No AI text generation, no training or fine-tuning of a model.
- No drafting of documents (privacy notices, policies, contracts).
- No certification study or teaching content.
- No legal advice or compliance determinations.
- No user accounts or authentication.
- No collection or storage of visitor queries. Searches run in the browser and never leave it.
- No paywalled or unofficial sources in phase 1.

## 4. Scope

### Phase 1
| Document | Type | Official source |
|---|---|---|
| GDPR (Regulation (EU) 2016/679), articles and recitals | law | EUR-Lex |
| CCPA/CPRA (Cal. Civ. Code 1798.100 et seq.) | law | California Legislative Information |
| CPPA CCPA regulations (Cal. Code Regs. tit. 11, 7000 et seq.) | regulation | California Privacy Protection Agency / OAL |

### Phase 2
- LGPD (Brazil), PIPEDA (Canada), GLBA (Privacy Rule and Safeguards Rule)
- Selected US state laws (start with Virginia, Colorado, Texas)
- Guidance on core program operations:
  - DPIA/PIA: EDPB/WP29 DPIA guidelines, ICO DPIA guidance
  - ROPA: ICO and EDPB guidance on records of processing
  - DSAR workflows: ICO and EDPB guidance on data subject rights
  - NIST Privacy Framework
- Additional guided topics for each added law

### Document type tags
Every document is tagged `law`, `regulation`, or `guidance`. LGPD's official text is Portuguese, so English versions are flagged `unofficial_translation`.

## 5. Architecture

```
BUILD (on my computer, and later GitHub Actions)
Official sources -> Fetch -> Parse -> Chunk + tag -> Validate
                                          |
                       Generate static site: article pages, search index,
                       guided topic pages, compare data
                                          |
                                  Push to GitHub
                                          |
HOSTING                         GitHub Pages (free, static)
                                          |
VISITOR'S BROWSER        Search index loads in browser, search runs locally
```

### Proposed stack (defaults, open to change)
- **Build pipeline:** Python 3.11+ scripts (fetch, parse, chunk, tag, validate, generate)
- **Working store during build:** SQLite or plain JSON files
- **Site generation:** static HTML pages generated by the Python build (or a simple static site generator such as Eleventy or Astro if Claude Code recommends it at step 1)
- **Search in the browser:** Pagefind (static search library that builds its index at build time and loads small index pieces on demand). MiniSearch (single JSON index loaded into memory) is the fallback. Evaluate both at step 3 and keep the one that handles section-number lookup and synonyms better.
- **Synonym and query handling:** a JavaScript layer that expands the visitor's query before searching (see section 9)
- **Hosting:** GitHub Pages from a public GitHub repository, deployed by a GitHub Actions workflow on each push
- **Config:** one `sources.yaml` listing every document, URL, type, jurisdiction, and parser; one folder of YAML files defining guided topics; one `synonyms.yaml`

### Hosting constraints
- GitHub Pages serves static files only. There is no server, database, or backend code at runtime.
- Pages is free for public repositories. The repository must be public.
- GitHub documents size and traffic limits for Pages sites (published site size, per-file size, monthly bandwidth). Check the current limits at step 1 and keep generated output well under them.
- The site can live as a project page under my existing GitHub account (for example, `username.github.io/privacy-tool`). A custom domain is optional and not required.

### Optional later enhancement: in-browser semantic search
A small embedding model can run in the browser (for example, via Transformers.js) with embeddings for each chunk computed at build time. This adds meaning-based matching with no server cost, at the price of a one-time download of tens of megabytes for visitors. It is not part of the first launch. Decide after measuring how well keyword search, synonyms, and guided topics perform on the test queries.

## 6. Data model (build time)

### `documents`
| Field | Notes |
|---|---|
| doc_id | short key, e.g. `gdpr` |
| title | full official title |
| jurisdiction | EU, US-CA, US-Federal, BR, CA, etc. |
| doc_type | law / regulation / guidance |
| source_url | official URL |
| version_label | amendment or consolidated version identifier |
| effective_date | if known |
| retrieved_at | date and time pulled |
| language | en / pt / etc. |
| is_translation | boolean |
| raw_path | path to saved original file |
| checksum | hash of the raw file, to detect changes |
| license_note | reuse terms and required attribution |

### `chunks`
| Field | Notes |
|---|---|
| chunk_id | stable id, e.g. `gdpr:art:35:1` |
| doc_id | foreign key |
| hierarchy | structured path, e.g. Chapter IV > Section 3 > Article 35 > Paragraph 1 |
| section_ref | human citation, e.g. `GDPR Art. 35(1)` |
| heading | section title |
| text | exact source text, unmodified |
| parent_chunk_id | links paragraph to article to chapter |
| token_count | for size checks |
| topics | tags, see section 8 |
| permalink | stable URL path on the site |

### `topics`
Controlled vocabulary of tags (DPIA, DSAR, ROPA, consent, breach notification, etc.) with synonyms.

### `crossrefs`
Links between chunks: explicit references inside the text ("as referred to in Article 6(1)") and manual concept links.

### `summaries`
| Field | Notes |
|---|---|
| chunk_id | foreign key |
| summary_text | plain-English summary |
| written_by | `manual` or `drafted-offline-reviewed` |
| reviewed_at | date I reviewed it |

Summaries are stored separately from source text, always labeled as summaries, and displayed only after I have reviewed them. They are written once at build time and never generated for visitors.

### `guided_topics`
Defined in YAML files, one per topic. Structure in section 10.

## 7. Ingestion and build pipeline

1. **Fetch:** Download each document from its official URL (prefer structured formats: eCFR API/XML, EUR-Lex HTML/Formex, official HTML). Save the raw file unchanged. Record checksum, URL, and retrieval date.
2. **Parse:** One parser per source family (EUR-Lex, eCFR, California code, generic HTML/PDF). Output a normalized tree of Part, Chapter, Section/Article, Paragraph, Subparagraph.
3. **Chunk:** Split by legal structure (rules in section 8).
4. **Tag:** Apply metadata and topic tags.
5. **Validate:** Automatic checks after each document:
   - Expected article/section count matches the known structure (GDPR: 99 articles, 173 recitals)
   - No empty chunks and no chunks above the size ceiling
   - Section numbering is continuous with no gaps
   - Spot-check report listing 10 random chunks against the source
   - Every provision cited by a guided topic exists in the loaded text
6. **Generate:** Build static pages (one per article or section, with paragraph anchors), the search index, guided topic pages, the compare data, and the Sources page.
7. **Re-run safely:** The build is idempotent. Re-running updates changed documents and leaves unchanged ones alone.

## 8. Chunking and tagging rules

- The primary unit is the smallest self-contained provision (usually a paragraph or lettered item), stored with its parent article and heading for context.
- The full article stays retrievable as a parent. Search returns the paragraph; the page can expand to the whole article.
- Never split mid-sentence. Never merge unrelated sections to hit a size target.
- Definitions sections (GDPR Art. 4, CCPA 1798.140, 45 CFR 160.103 and 164.103/164.501) are chunked per defined term.
- Recitals are separate chunks with their own type, linked to the articles they relate to where the source makes that link.
- Each chunk carries `law`, `jurisdiction`, `section_ref`, `doc_type`, `source_url`, `retrieved_at`, and `topics`.
- Initial topic vocabulary: DPIA/PIA, DSAR/consumer rights (access, deletion, correction, portability, opt-out), ROPA/record-keeping, lawful basis/consent, notice/transparency, cookies and tracking, data breach notification, vendor/processor contracts, cross-border transfers, security safeguards, children's data, sensitive/health data, enforcement/penalties, definitions, scope/applicability, exemptions.
- Topic tagging is a first pass of keyword rules, saved to a reviewable file so I can correct it. Manual corrections persist across rebuilds.

## 9. Search behavior (runs in the browser)

1. **Reference lookup:** If the query looks like a citation ("Art. 30", "1798.105", "164.502(b)"), jump straight to the exact match.
2. **Keyword search with boosts:** Ranked full-text search. A match in a heading, definition, or defined term ranks above a match in body text. Exact phrase matches rank above scattered word matches.
3. **Query expansion:** Before searching, expand terms using `synonyms.yaml`. Examples: "erase" to "delete", "cookies" to "tracking technologies, sale, share, opt-out preference signal", "privacy notice" to "privacy policy, notice at collection", "DSAR" to "data subject request, consumer request, right of access".
4. **Long-question handling:** For a full sentence, strip filler words, keep the meaningful terms, and detect jurisdiction words ("California", "EU", "health") to suggest a law filter.
5. **Guided topic matching:** Match the query against each guided topic's trigger terms. Matching topics appear as cards above the search results.
6. **Filters:** Law, jurisdiction, doc type (law/regulation/guidance), topic.
7. **Result display:**
   - Citation (`GDPR Art. 35(1)`)
   - Exact source text with matched terms highlighted
   - Breadcrumb hierarchy
   - Link to the official source, plus version and retrieval date
   - Expand to the parent article and show cross-references
   - Permalink to the provision
8. **No results:** Show a plain message and suggest broader terms or a guided topic. Never fill the gap with unsourced text.
9. **Compare view:** Choose a topic and laws, get the relevant chunks in columns (for example, DSAR response deadlines under GDPR vs. CCPA vs. HIPAA access rights). Comparison sets are defined in YAML, not generated.

## 10. Guided topics

A guided topic is a hand-built research path for a common real-world question. It returns source material, not advice, and does not draft anything.

### Structure (one YAML file per topic)
- `id`, `title`, and a one-sentence `scope` statement
- `triggers`: words and phrases that surface the topic from a search
- `applicability`: the threshold questions, each linked to the defining provisions (does the law apply at all?)
- `items`: ordered checklist entries, each with
  - a short label (what the provision requires)
  - one or more `chunk_id` references (the exact text is pulled from the stored chunk, never retyped)
  - an optional short summary, marked as a summary
- `related`: other laws or topics that may also matter, with links
- Standing disclaimer line shown on every topic page

### Initial topics

**1. California business privacy notice**
- Scope: What California privacy law provisions address the content of an online privacy notice.
- Triggers: California, privacy notice, privacy policy, notice at collection, website, online business, small business
- Applicability: CCPA business thresholds (revenue, number of consumers or households, share of revenue from selling or sharing personal information) from the CCPA definitions; CalOPPA coverage of commercial websites collecting personal information from California residents
- Candidate provisions (confirm against ingested text): CCPA notice at collection requirements; CCPA privacy policy content and update frequency; CPPA regulations on notice at collection and privacy policy; CalOPPA required disclosures, including do-not-track disclosure
- Related: cookies and tracking topic; consumer rights topic

**2. Cookies and tracking (California)**
- Scope: What California privacy law provisions address cookies, trackers, and the sale or sharing of personal information collected through a website.
- Triggers: cookies, tracking, pixels, analytics, advertising, opt-out, Global Privacy Control, do not sell, do not share, website
- Applicability: same CCPA thresholds; definitions of "sell", "share", and "cross-context behavioral advertising"
- Candidate provisions (confirm against ingested text): right to opt out of sale or sharing; methods for submitting opt-out requests, including the "Do Not Sell or Share My Personal Information" link; regulations on opt-out preference signals; regulations on notice of right to opt out; CalOPPA do-not-track disclosure
- Related: California business privacy notice topic; EU consent requirements under GDPR as a comparison

### Authoring rules
- The provision list for each topic is reviewed by me against the ingested source text before the topic is published.
- Every topic page shows version and retrieval date for every cited provision and flags a topic as needing review when a cited provision changes during a rebuild.
- Topics describe what the law says. They never say "you must do X to be compliant."

## 11. Site pages

- **Home:** search bar, example searches, and the featured guided topics.
- **Search results:** result list with filters, guided topic cards on top, expand/collapse for each result.
- **Document browser:** pick a law, navigate its table of contents, read it in order.
- **Provision pages:** one per article or section, with permalinks to each paragraph.
- **Guided topics:** one page per topic.
- **Compare:** side-by-side view.
- **Sources:** every loaded document with version, retrieval date, official link, and reuse terms.
- **About:** scope, method, what the site is and is not.
- **Disclaimer and privacy notice:** reference tool, not legal advice; no accounts, no query logging, no analytics that identify visitors.
- **Feedback:** link to report an error (a GitHub issue form).
- Export: save a set of results to Markdown or print-friendly format.

## 12. Test queries (acceptance tests)

Each should return the correct provision, or guided topic where noted, in the top 3 results.

**Reference lookups**
1. "GDPR Article 30" returns the records of processing provision.
2. "1798.105" returns the CCPA right to delete.
3. "164.502(b)" returns the HIPAA minimum necessary provision.

**Concept questions**
4. When is a DPIA required under GDPR?
5. What must a record of processing activities contain?
6. What are the exceptions to the CCPA right to delete?
7. What is the HIPAA minimum necessary standard?
8. What is the deadline to respond to a data subject access request under GDPR?
9. How does CCPA define "sell" and "share"?
10. What are the breach notification timelines under GDPR vs. HIPAA?
11. What counts as a "business associate" under HIPAA?
12. What are the lawful bases for processing under GDPR?
13. What must a CCPA privacy notice include?

**Guided topic tests**
14. "I am building a sales business in California and have no idea what I should include in my privacy notice online, and I need to make sure the cookies on my website are set up right" surfaces both guided topic cards at the top.
15. "Do I need a Do Not Sell link" surfaces the cookies and tracking topic.
16. "Does CCPA apply to my small business" surfaces the applicability provisions.

**Behavior tests**
17. A query outside the loaded sources (for example, Canada's breach reporting threshold in phase 1) returns a clear no-results message and no invented text.
18. A query with different wording than the law ("erase my data") finds the right provision through synonym expansion.
19. Filtering to HIPAA only returns no GDPR or CCPA results.
20. Searching works with no network calls after the page and index have loaded (confirm in browser dev tools that query text is never sent anywhere).

I will add more queries as I use the tool. Failures become regression tests.

## 13. Build order

Each step ends with something I can run or open and verify. Do one step at a time and stop for review.

1. **Skeleton and hosting proof:** Project folder, dependencies, `sources.yaml`, README, and a minimal "hello" page deployed to GitHub Pages through GitHub Actions. Confirm the public URL works and note the current Pages limits.
2. **Ingest GDPR:** Fetch, parse, chunk, validate. Show me a sample of chunks and the validation report.
3. **Static search over GDPR:** Generate article pages and the search index. Build the search page with citation lookup. Compare Pagefind and MiniSearch and keep the better one. Run tests 1, 4, 5, 12.
4. **Synonyms, boosts, and query handling:** Add `synonyms.yaml`, heading boosts, and long-question handling. Report which tests pass.
5. **Ingest CCPA/CPRA, CPPA regulations, and CalOPPA:** Same checks, new parsers as needed. Run the CCPA tests.
6. **Ingest HIPAA (45 CFR 160 and 164):** Same checks. Run the HIPAA tests.
7. **Filters, document browser, and permalinks.**
8. **Topic tagging:** Controlled vocabulary, first-pass tagging, review file, topic filter.
9. **Guided topics:** Build the guided-topic engine and the two initial topics. I review the provision lists. Run tests 14 to 16.
10. **Compare view.**
11. **Trust pages:** Disclaimer, About, privacy notice, Sources, feedback link. Confirm source reuse terms and add attributions.
12. **Public launch:** Make the repository public if it is not already, confirm the automated build and deploy, test on a phone and a different network, run test 20, then share the link.
13. **Phase 2 documents, guidance, and topics**, one at a time, each with its own tests.
14. **Optional: in-browser semantic search**, only if the test results show keyword search is missing too many questions.

## 14. Definition of done (launch)

- All phase 1 documents built with passing validation checks.
- At least 18 of the 20 test queries pass; failures are documented.
- Both initial guided topics are reviewed and published.
- Every displayed result shows citation, exact text, official link, version, and retrieval date.
- Public URL works on desktop and mobile with no login.
- Disclaimer, About, Sources, and privacy notice pages are live.
- No query text is sent to any server.
- Source licensing is confirmed and attributions are displayed.
- A new document can be added by editing `sources.yaml` and, if needed, adding one parser.
- A push to GitHub rebuilds and redeploys the site automatically.

## 15. Known risks

- **Parsing differences:** Each source publishes in a different structure; parser work is likely the largest time cost.
- **Keyword search limits:** Questions phrased very differently from the law's wording can miss. Synonyms, guided topics, and the optional semantic step are the mitigations.
- **Curation effort:** Guided topics and synonym lists require manual work and review. They are also the most valuable part of the site.
- **Versions change:** Laws and regulations are amended. Version labels, retrieval dates, and the needs-review flag keep results from being presented as current without a date.
- **Guidance is not law:** Guidance chunks must be visually and structurally distinct from binding text.
- **Translations:** Non-English official texts and English translations need clear labeling.
- **Summary accuracy:** Summaries are written or reviewed by me, labeled, and always shown next to the source text.
- **Not legal advice:** The tool is a research aid. Guided topics describe what provisions say, not what a business must do.
- **Public reliance:** Visitors may rely on results. Version dates, an error-reporting link, and a visible disclaimer are required.
- **Static hosting limits:** Site size and bandwidth have limits on GitHub Pages. Index size must be monitored as documents are added.
- **Source terms:** Reuse conditions differ by publisher and must be checked before launch.
- **Public repository:** The repository and its contents are visible to everyone.
